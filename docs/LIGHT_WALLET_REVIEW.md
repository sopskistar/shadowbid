# Public testnet receiving monitor: time-boxed review

Reviewed 2026-10-24. No alternate payment provider was enabled. The current Zallet/Zebra worker remains the only implementation connected to ShadowBid invoices, and only its **local regtest** receiving path has been exercised with wallet evidence and three confirmations.

| Approach | Evidence | Integration decision |
| --- | --- | --- |
| A. Z3 Zebra + Zallet | Existing worker assigns Zallet-owned receivers, reads unspent shielded notes, checks Zebra chain height, reconciles integer zatoshis, and waits for three confirmations. This passed local regtest. Zebra 7.0.0 is still synchronizing public testnet; pinned Zallet beta.1 has not been checked against post-NU7 transactions. | Preserve it. Do not start testnet Zallet or issue real invoices until Zebra reaches tip and wallet RPC behavior is checked. |
| B. Zingo/Rust light wallet | [Zingo PC](https://github.com/zingolabs/zingo-pc) documents testnet and viewing-key import, and uses a local light-wallet scanner fed by lightwalletd. [Zingolib CLI](https://github.com/zingolabs/zingolib) supports noninteractive commands, but its releases are described as provisional. No Zingo CLI binary is installed locally, and no stable machine-readable API for unique invoice receivers, note-to-receiver matching, and reorg-safe confirmations has been validated here. [librustzcash](https://github.com/zcash/librustzcash/blob/main/zcash_client_backend/CHANGELOG.md) has Ironwood scanning support, but building a reliable wallet service on its APIs is a separate security-sensitive project. [ZODL Slipstream](https://github.com/zodl-inc/slipstream) is a sync engine, not a drop-in receiving monitor. | Promising follow-up, but not a safe replacement before the deadline without an independent end-to-end receiving test. |
| C. Hosted lightwalletd + local scanner | [ZEC.PRO](https://zec.pro/) advertises a public testnet lightwalletd endpoint. [lightwalletd](https://github.com/zcash/lightwalletd) supplies compact chain data, not recipient-wallet ownership proof or an invoice ledger. A local trusted wallet must still derive assigned receivers, decrypt notes, reconcile exact zatoshis, and handle chain reorganizations. A hosted server also observes client IP and scanning behavior and can delay or omit data. | Useful as a future light-wallet data source; do not send viewing or spending keys to it or treat its responses alone as payment confirmation. |

The [ZIP-321 standard](https://zips.z.cash/zip-0321) specifies the payment request; it does not provide receipt evidence. A browser click, user-entered transaction ID, explorer result, or hosted lightwalletd response by itself cannot confirm an invoice. NEAR Intents remains roadmap work.

## Gate before considering a light-wallet adapter

Use a dedicated **local, trusted testnet receiving wallet**, ideally with a limited viewing authority if the chosen wallet supports the required receiver derivation. Demonstrate: network-specific address generation; proof each assigned address belongs to that wallet; distinct addresses per invoice; decryption of a real incoming shielded note; exact amount and receiver matching; three chain confirmations; duplicate and partial payment handling; and rollback after a reorganization. Capture the actual wallet output formats and test the existing signed worker-to-app channel. No spending key or full viewing key belongs in the browser or Vercel environment.

Public testnet funding remains an external blocker. Do not classify unit fixtures or the existing regtest transaction as public testnet evidence.

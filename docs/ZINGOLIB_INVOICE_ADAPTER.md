# Zingolib note recipient adapter

The pinned NU7-compatible Zingolib CLI reports wallet-owned note values, txids, output indexes, and heights, but its `notes` JSON omits the decrypted recipient. Account 0 and a txid cannot identify an invoice. The source patch in [`../patches/zingolib-invoice-recipient.patch`](../patches/zingolib-invoice-recipient.patch) adds `recipient_unified_address` to each note summary by comparing the decrypted Orchard, Ironwood, or Sapling recipient with the Unified receivers recorded by that wallet. Unknown or internal recipients produce `null`; an invoice monitor must reject them.

The patch applies to Zingolib commit `4d85349f3cab5f7e4e5273c7f01c34044f17b1a9`, the source of the isolated receiver image. On 2026-10-26 it passed `cargo check -p zingo-cli --offline` inside the existing local source image and a release build. A read-only `--offline --nosync notes` run against the protected wallet resolved the real 1 TAZ faucet note's recipient to the existing wallet-controlled testnet Unified address. `SHADOWBID_ZINGO_INVOICE_CLI=/path/to/patched/zingo-cli python3 scripts/receiver-observe.py` repeated the result and durably recorded the note, address, amount, block height, and active-chain confirmations in the private gitignored observation log. The scanner was restarted after each offline snapshot. No seed, spending key, memo, or faucet request ID was emitted by the observation script.

To reproduce the build from a clean checkout of that exact Zingolib commit, apply the patch at the Zingolib root with `patch -p1 < /path/to/shadowbid/patches/zingolib-invoice-recipient.patch`, then run `cargo check -p zingo-cli --offline` and `cargo build -p zingo-cli --release --offline` in the same pinned Rust environment as the receiver image. Install the resulting binary in a private operator-controlled location. `receiver-observe.py` mounts it read-only into an offline container when `SHADOWBID_ZINGO_INVOICE_CLI` is set; it rejects a patched CLI that omits recipient metadata. Without the adapter, the script can still observe wallet-owned notes but does not supply invoice routing evidence.

This proves **recipient identification for the existing faucet note**, not invoice-specific settlement. Two distinct wallet-controlled receivers are now persistently assigned to isolated owner test invoices. Their bindings survived app and observer restarts; real receiver checkout and synthetic failure tests passed. Neither invoice has a matched payment. The remaining gate is a real payment to an assigned receiver, identified by its decrypted recipient and exact integer-zatoshi amount through three active-chain confirmations, with isolation and recovery verified in the paid state. See the [continuation record](INVOICE_EXPERIMENT.md) for test results, preserved state, and reproduction commands. Keep the production payment worker disabled until then.

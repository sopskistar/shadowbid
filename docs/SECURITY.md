# Security review

Authentication uses bcrypt password hashes, random 32-byte session tokens stored only as SHA-256 hashes in PostgreSQL, HttpOnly SameSite cookies, server-side session lookup, and Origin checks on browser mutations. Logout deletes the server-side session. PostgreSQL-backed atomic limits allow eight login attempts and five signup attempts per email in fifteen minutes. Signup does not reveal whether an existing address is registered. These limits do not prevent signup abuse across many addresses; add an abuse service or trusted edge IP limit before open production use.

Production signup returns 503 until `EMAIL_VERIFICATION_MODE=resend`, `RESEND_API_KEY`, `EMAIL_FROM`, and `PUBLIC_APP_URL` are configured. The owner reports these values and Resend sending DNS are configured, but no email was sent in this workspace, so delivery remains unverified. Verification tokens are random, hashed in PostgreSQL, single-use, and expire after 24 hours. Correct credentials do not permit login before verification when provider mode is enabled. There is no password recovery flow; losing a password requires operator support. Local development may allow unverified signup, without labeling the email verified. `LOCAL_AUTH_BYPASS` works only with a loopback PostgreSQL URL, short-auction mode, and no Vercel environment.

Bid reveals bind the authenticated bidder, auction ID, amount, and secret to the original commitment. One commitment per bidder is database-constrained. Server/database deadlines govern writes. Finalization uses an advisory transaction lock and unique invoice per auction. Public auction responses omit bid amounts and identities. Checkout requires a high-entropy token plus the winner or seller session. The seller view does not show the receiving address. Checkout tokens in URLs can enter server logs; hosting log retention should be minimized.

Worker endpoints require timestamped HMAC with a unique PostgreSQL nonce. The worker checks wallet account and shielded receiver type, deduplicates note outputs, cross-checks against Zebra when configured, and requires three confirmations. A client cannot submit a txid to confirm payment. New notes discovered after invoice expiry require manual review. A later missing note can lower payment status after a reorganization.

The judge route uses separate session and bid tables, a hashed 32-byte HttpOnly capability cookie, database deadlines, and a three-session-per-15-minute limit keyed by HMAC of the trusted Vercel forwarded client IP. It never creates a customer invoice or payment receiver. Expired rows are rejected immediately and purged in bounded batches when a new practice starts. A visitor playing both roles can see both receipts; this is an educational flow, not a privacy claim against that visitor. CSV staging requires an authenticated seller, explicit authority attestation, row validation, and a matching DNS TXT response before activation. TXT evidence shows limited control, not legal ownership.

**Remaining risks:** Custom authentication has not been independently audited. Worker or database compromise can forge or alter status; the operator can read revealed amounts and invoice records. Zallet is beta and wallet RPC behavior varies by version. The worker host holds wallet authority; no spending or viewing key belongs in Vercel. Unspent-note polling assumes dedicated invoice accounts are not spent. There is no escrow, automatic seller payout, registrar proof, dispute system, or automated recovery. Do not use mainnet or high-value assets.
